# 挑選模組合約(pick contract)

一個「自適應挑選策略」在本專案就是一個**挑選模組**:一支自足的 JavaScript ES module,於每個決策日只憑過去的資訊,從策略庫(數萬隻策略;隻數為 `ctx.n`)挑出一組策略;評估器再用這組策略其後的實際訂單算績效。

## 1. 模組形狀

```js
export const meta = { arms: ['A04_act'], params: { … }, desc: '一句話說明' }   // 選配, 但請寫: 審計會看

export default function pick(ctx) {      // 必要: 回傳策略序號之陣列, 或 { ids, tag }
    …
    return ids
}

export function accept(sig, book) {      // 選配: 逐訊號之執行規則(回 true 才下單); 不寫 ⇒ 全收
    return book.open < 30
}
```

限制(由 `g_eval.mjs` 靜態檢查,不過即拒收):

- 不得 `import` / `require` 任何模組;不得用 `process`、`globalThis`、`eval`、`Function`、`fetch`、檔案與行程介面、計時器。
- 不得用 `Date.now()`、無參數之 `new Date()`、`Math.random()`:時間用 `ctx.time` / `ctx.bar`,亂數用 `ctx.rand()`(可重現)。
- 結果只能由 `ctx`(與 `sig`、`book`)決定;同一模組重跑,選集必須逐位相同(評估器以 `selHash` 核對)。
- **不得硬編策略序號清單**(序號只是策略檔排序後之位置,硬編等於把答案寫死,審計會判不可信)。

執行期之約束(評估器強制;違反即該次評估失敗):

- **不得改寫內建物件**(原型之方法與存取子、全域之建構子、`Math`、`JSON`、`Reflect`、`Object`、`Array`、定型陣列、`console` 等之方法;含暫時改寫後再改回)。評估器於載入模組後、評估器各方法之入口、每次呼叫 `pick` 後、每批 `accept` 呼叫(一次逐訊號模擬)後、擴充診斷每個診斷後與其 `api` 函數之入口、延遲讀入帳本欄前,以及 `g_eval.mjs` 讀帳本前與輸出前,比對受保護之內建物件(清單見套件 `sgud/rule/rulebook.md` R-EV-35),被改即評估失敗:錯誤之 `code` 為 `EVAL_INTEGRITY`,訊息列出被改之項目,`g_eval.mjs` 印 `ERROR EVAL_INTEGRITY …`、離開碼 3。模組頂層之程式與延後執行之程式(`Promise.then` 等)同樣受檢。**偵測之界線**:兩次比對之間改而又改回者偵測不到(其間評估器只用載入時擷取之參照,不受影響,但仍屬違約,審計會判);受保護清單以外之內建物件不在比對內。
- **不得改寫 `ctx` 交出之物件與 `accept` 收到之 `sig`、`book`**:它們是複本或凍結 / 封裝之物件,改它們不會改變評估器之任何數字(改不動者拋錯,該次評估失敗)。
- **`ctx` 之函數只在該次 `pick` 呼叫內有效**:把 `ctx` 留到其後(其後之決策、其他相位、`accept`)再呼叫其函數即拋錯。
- **`tag` 只收可結構化複製之資料**(數值、字串、布林、物件、陣列、Map、Set、Date、RegExp、定型陣列、ArrayBuffer、DataView、錯誤物件;不得含函數、符號、共享記憶體與其他宿主物件),**於 `pick` 回傳時取快照**並凍結:回傳之後再改原物件,不影響已記錄之 tag;`accept` 收到的是唯讀之快照(含 Map、Set、Date、RegExp、定型陣列等凍結擋不住之內容者,每次呼叫 `accept` 另給一份複本)。tag 於歸因與分佈以 JSON 表示:BigInt、循環參照之 tag 可取快照,但歸因時評估失敗;Map、Set 之 tag 於歸因中皆表示為 `{}`(不同之 Map 併為同一列)—— 要分類就用字串或數值。

只靠本合約與審計(執行期不強制):

- **模組層變數不得跨相位、跨模擬保存狀態**:要跨決策記住的東西放 `ctx.state`(每相位重新開始);`accept` 不得讀寫模組層變數(§4)。
- 檔案、行程、網路介面之取用:上列靜態檢查為字樣層級之防呆(以字串組出名稱、間接取得全域物件等寫法檢查不到),審計仍讀碼。
- 擴充診斷不得把較晚做出之選集挪到較早之決策使用(§7):`api.phases` 給的是整段期間之選集,`simulate` 只核對相位數與決策數,不核對選集之時序;`api.market` / `factor` / `series` 之 `bar` 只核對為 0 ~ K 棒數之整數,不核對它是否為所分組之決策自己之決策棒或更早者。
- 同一相位內各次決策共用同一份 `ctx.meta`(§3):改它只改了自己其後之輸入,評估器察覺不到,仍屬違約。

## 2. 決策節奏與評估

- 每 7 日決策一次;七個起始相位(日)各跑一遍取平均。第一個決策日在數據起點後 180 日(暖機)。
- 每次決策呼叫一次 `pick(ctx)`;回傳之策略於其後 7 日內的每個進場訊號,依時間先後逐一問 `accept(sig, book)`;回 `true` 的才算下單。
- 一張單 = 1 單位;損益於出場實現(含手續費)。**等效年化 = 總損益 ÷ 最大同時持倉單數 ÷ 年數**。
- **期間**:
  - 訓練期(2022-07-01 ~ 2025-10-06)= 策略庫之求解期。每隻策略都是以這段資料求得(做多策略之求解窗止於 2025-04-08,做空止於 2025-10-06),所以訓練期內任何挑法(含隨機挑)都賺錢。**訓練期之績效不是目標,也不是挑法有效之證據**;訓練期之歷史是找結構與特徵之材料。
  - **回測期(2025-10-06 ~ 2026-07-31)= 評估期**。策略庫沒見過之期間;同一批策略在此隨機挑之等效年化為負。**本專案之目標:使回測期之等效年化更佳(穩定之正值)。`g_eval.mjs` 預設就評估回測期**,可以反覆回測、看完整數字。
  - 2026-08-01 以後之資料不提供,任何節點與做夢任務皆不使用。
- **評估回測期時 `ctx` 之行為**:
  - 挑選函數**自數據起點(暖機後之第一個決策)連續執行到回測期終點**:訓練期那一段照跑(讓 `ctx.state` / `ctx.prev` 延續),**只有決策日落在回測期者計入績效**;回測期起點之持倉簿(`book`)是空的。
  - 每個決策只看得到決策棒以前之資訊:`ctx.stat(0)` 之「全部歷史」自數據起點起算,含訓練期之全部與回測期內、決策日以前之單;`ctx.stat(days)`、`ctx.orders`、`ctx.entryDays`、`ctx.entryBars`、`ctx.exitDays`、`ctx.exitBars`、`ctx.market`、`ctx.factor`、`ctx.series` 同樣以各決策日為界。
  - `ctx.k` 自數據起點之第一個決策起算並一路續編,`accept` 收到之 `sig.k` 亦同;`ctx.nDecisions` 是該次執行之決策總數(含訓練期那一段)。
  - `ctx.meta.ntAll` 與 `ctx.meta.fitEndBar` 是策略庫之靜態屬性(`ntAll` 只計訓練期之進場數),不隨決策日改變。
  - `ctx.rand` 依(相位、`ctx.k`、亂數種子)播種;迴圈另以不同之亂數種子重放成品,其結果列於節點文件(含隨機抽取之成品,結果會隨種子波動)。
- **不得把回測期之答案寫進模組**:不以 `ctx.k`、`ctx.day`、`ctx.time` 之特定值或區間寫死行為(例如「第 N 次決策起換一套規則」「某月之後關閉某側」),不硬編日期或由回測期結果反推之常數清單 —— 審計會判不可信。依**當下可觀察之狀態**(行情、策略近期之行為、選集之組成)切換才是自適應。回測期之結果只能經由「你依結果改進機制」影響挑法。
- 回測期只有約 10 個月:參數看平原(鄰近之值同向)不看單點最高,七個相位同向比平均高更重要。
- `--period train`:同一模組改看訓練期內之決策(**診斷用**;樣本內,不計入判讀,也不記入交付)。
- `--period postfit`:求解窗後段(**診斷用;此結果不是正本**;只是佐證,不入 S、階梯與看板之排序 —— 結果檔之 `score` 為 `null`、不印判讀列)—— 挑選函數照常執行,只計決策棒落在「最早之求解窗終點棒之次一根 ~ 回測期起點」之決策,且每個決策只留「求解窗之終點棒早於決策棒」之席(策略未見過之期間;求解窗之終點見設定 `eval.fitEnd`)。輸出所留之席之等效年化、組成對照(同側同活躍度;只換所留之席)之超額與 p、下單數,與前段 / 後段(依決策序各半;各段自空倉起算)之同一組量(結果檔之 `metrics.afterFit`);另列**近 90 日活躍度版之組成對照**(活躍度改為決策日以前最近 90 日之進場數;全段與前段 / 後段之超額、z、p;`metrics.afterFit.sideActRecent` 與各段之同名欄)—— 所留之席近期比其累計之同儕更活躍或更安靜時,與累計活躍度版同向才算穩(擴充診斷於此段不載入,故另列)。用途是驗證「一條線之內容換期是否仍成立」;以之挑參數即失去其獨立性。**效度限制**:此段內,決策棒以前之單多在求解窗內;以過往之損益為輸入之排序鍵,其輸入於此段之前段多為樣本內之單 ⇒ 看分段;以進場時點或結構為輸入之鍵不受此限;同劑量 / 同訊號量 / 同活躍度虛無之替換池為全庫 ⇒ 此段讀組成對照;最後一個決策之視窗可跨過回測期起點至多一個決策間隔。須有虛無(`--mode full` 或 `--null N`,N ≥ 1);每個所評估之相位須於段內有決策棒(否則不評估);不與 `--ref`、`--ext-test` 併用,擴充診斷不載入;`--member`、`--phases` 可併用。

## 3. `ctx`(pick 的唯一輸入)

| 欄位 | 內容 |
|---|---|
| `ctx.n` | 策略數;策略以序號 `0 … n-1` 表示 |
| `ctx.bar`、`ctx.day`、`ctx.dow`、`ctx.time` | 決策棒序號(4 小時一根)、日序號、星期(0 週日 … 6 週六)、時間字串 |
| `ctx.k`、`ctx.phase`、`ctx.nDecisions`、`ctx.cadenceDays` | 本相位第幾次決策、相位、本相位決策總數、決策間隔日數 |
| `ctx.stat(days)` | 全部策略於「決策日以前最近 `days` 日」之統計(`days` 給 0 = 全部歷史)。回傳物件之各欄為長度 `n` 之陣列:`closed`(已出場單數)、`wins`(其中獲利者)、`pnl`(已出場單之損益和)、`entries`(進場單數,含未出場)、`open`(決策當下仍未出場之單數,與 `days` 無關)、`lastEntryAgo`(距最近一次進場之 K 棒數;從未進場為 1e9)。**陣列會被重複使用,只在本次 `pick` 呼叫內有效,不要跨決策保存引用**(要留就自己複製);回傳之物件凍結(各欄不可換成他物) |
| `ctx.orders(s)` | 策略 `s` 於決策日以前之全部進場單:`[{ ent, ext, pnl }]`(`ent` 進場棒;尚未出場者 `ext`、`pnl` 為 `null`)。較慢,只對少數候選使用 |
| `ctx.entryDays(s, days)` | 策略 `s` 最近 `days` 日內各進場單之日序號(Int32Array;供算進場日集合之重疊) |
| `ctx.entryBars(s, days)` | 策略 `s` 於決策棒以前、最近 `days` 日內各進場單之**進場棒序號**(Int32Array 之複本;由舊至新;與 `ctx.entryDays(s, days)` 同序、同長;`days` 省略或 0 = 全部歷史)。`Math.floor(棒序號 ÷ 每日棒數)` = 日序號(4 小時棒 ⇒ 每日 6 根;棒序號與 `ctx.bar`、`ctx.market`、`ctx.factor` 之棒同一座標:進場棒距決策棒 `ctx.bar − 棒序號` 根)。成本與 `ctx.entryDays` 同級,可對全庫每次決策呼叫;供日內層級之進場時刻結構(進場時段、進場棒在當日之位置)與以進場棒之價為準之計算。只含進場棒早於決策棒者 |
| `ctx.exitDays(s, days)` | 策略 `s` 於決策棒以前、最近 `days` 日內**已出場**之各單之出場日序號(Int32Array;依出場時間由舊至新;`days` 省略或 0 = 全部歷史)。與 `ctx.entryDays` 對稱,成本同級;只含出場棒早於決策棒者。供出場側之結構與指紋(出場日之量能、價位位置等);不必為此對大量策略呼叫 `ctx.orders` |
| `ctx.exitBars(s, days)` | 策略 `s` 於決策棒以前、最近 `days` 日內**已出場**之各單之**出場棒序號**(Int32Array 之複本;依出場時間由舊至新;與 `ctx.exitDays(s, days)` 同序、同長;`days` 省略或 0 = 全部歷史)。`Math.floor(棒序號 ÷ 每日棒數)` = 出場日序號;棒序號之座標同 `ctx.entryBars`。成本與 `ctx.exitDays` 同級;供出場側之棒層級結構(出場棒之時段、出場棒之價量狀態)。只含出場棒早於決策棒者 |
| `ctx.market(nBack)` | 標的於決策棒以前最近 `nBack` 根 K 線:`{ open, high, low, close, volume }`(由舊至新;不含決策棒) |
| `ctx.factor(ki, nBack)` | 因子 `ki`(序同 `ctx.meta.keyNames`,共 `ctx.meta.keyNames.length` 個)於決策棒以前最近 `nBack` 根 K 棒之值(Float64Array 複本;由舊至新;不含決策棒;缺值為 `NaN`;`nBack` 預設 180,超過已有之棒數者只給到數據起點)。即策略觸發進場所用之同一份序列(原值):**策略於某棒進場 ⇔ 其各條件於該棒皆有值(非 `NaN`)且全部成立**(條件見 `ctx.meta.keySym` / `keyTh`)。`keyNames` 以 `index_` 開頭者取自標的之溢價指數、`price_` 開頭者取自標的之價量,皆為標的自身之資料。成本(每次決策;以約 900 個因子、33 萬個條件之策略庫為例):各取全部歷史約 0.02 秒,另加排序約 0.3 秒,全部條件各掃近 180 根約 0.13 秒 —— 一次完整評估約 1,300 次決策,**跨決策不變或緩變之量(例如門檻在該因子分佈中之分位)放 `ctx.state`、隔數次決策才重算** |
| `ctx.series(name, nBack)` | 外部序列 `name`(`ctx.meta.seriesNames` 之一)於決策棒以前最近 `nBack` 根 K 棒之值(Float64Array 複本;由舊至新;不含決策棒;缺值為 `NaN`;`nBack` 預設 180,超過已有之棒數者只給到數據起點;慣例同 `ctx.factor`)。外部序列 = 策略庫以外、屬標的自身之序列,由專案備妥並於建帳本時對位到 K 棒(各名稱之定義、單位與缺漏情形見專案之說明);帳本未建入者 `ctx.meta.seriesNames` 為空陣列,名稱不在其內者拋錯(訊息列出可用之名稱)。**時間標記之約定與使用端之責任見下方「外部序列之時間標記」** |
| `ctx.meta` | (每次執行〔每個相位〕另給一份複本:物件凍結、各陣列為複本;改它不影響評估器、其他相位與擴充診斷 —— 同一相位內各次決策共用同一份,改它只改了自己其後之輸入,等同改自己之狀態,仍屬違約)策略之靜態結構屬性(長度 `n` 之陣列;另含 `seriesNames`:外部序列之名稱陣列〔凍結〕,見 `ctx.series`):`mode`(1 做多 / -1 做空)、`tp`、`sl`(止盈止損比例)、`nKeys`(因子數)、`cls`(每策略 3 格:一般類 / 指數類 / 成交量類因子數,取 `cls[s*3+j]`)、`keyOff` + `keyIdx` + `keyNames`(策略 `s` 之因子名 = `keyNames[keyIdx[i]]`,`i` 自 `keyOff[s]` 至 `keyOff[s+1]-1`)、`keySym` + `keyTh` + `keyOr`(進場規則之各條件,與 `keyIdx` 逐格對齊:條件 `i` 成立 ⇔ 因子 `keyIdx[i]` 之值 `> keyTh[i]`(`keySym[i]` 為 1)或 `< keyTh[i]`(`keySym[i]` 為 -1);`keyOr[i]` 為 1 者是「或」條件 —— 本庫全為 0,即各條件皆須成立)、`ntAll`(整段訓練期之進場數)、`tie`(各策略固定之亂數,Uint32;排序同分時之次鍵)、`fitEndBar`(各策略求解窗之終點棒:做多 = 2025-04-08、做空 = 2025-10-06 所對應之棒序號;此棒以後進場之單才是該策略「沒見過之期間」所產生,可用 `ctx.orders(s)` 之 `ent >= fitEndBar[s]` 篩出;訓練期內做空策略尚無此類單)、`barsPerDay`(6) |
| `ctx.state` | 本相位內跨決策保存之物件(每相位開始時為 `{}`);要記住上次的東西放這裡 |
| `ctx.prev` | 上一次決策之選集(已排序之 Int32Array 之**複本**;第一次為空;改它不影響已記錄之選集) |
| `ctx.rand()` | 可重現之亂數(0 ~ 1)。**每次決策依(相位、決策序)重新播種**:每次決策內 `ctx.rand()` 之呼叫順序相同之兩個模組,會得到相同之亂數 ⇒ 要做「同種子之配對對照」,只需讓兩個版本每次決策之呼叫順序相同(例如先固定抽好候選,再套用不同之規則);另寫一個呼叫順序不同之隨機版不是配對對照。在 `ctx.state` 內就地洗牌之池,一旦某次決策之消耗不同,其後之順序即一直不同 |

注意:

- **外部序列之時間標記(`ctx.series`)**:序列檔 `<名>.json` 為 `[{ time, value }]`(格式同因子檔;檔名以底線起首者略過;名稱限英文字母起首之英數與底線、至多 32 字)。`time` = K 棒之**開盤時間**,與 K 線檔之 `time` 同一字串格式(如 `2022-07-01T00:00:00`;格式不同者對不到棒);`value` 須為有限數(數字或數字字串),缺值之棒不列(取得時為 `NaN`);同一時間有多筆有效值而相異者(互相矛盾),該棒視為缺值(與列之順序無關,建帳本時於記錄提示),值相同者無影響。評估器之決策時點 = 決策棒之開盤 = 前一棒之收盤:`ctx` 之各介面只含棒序 < 決策棒者,序列亦同 —— 即序列之值**視為於其標記之棒收盤時已得知**(與因子、K 線之收盤價同一約定)。**使用端之責任**:該量得知之時點須不晚於所標記之棒之收盤時間(= 該棒開盤時間 + 每根小時數);若要在該棒收盤之後才得知(例如該棒結束後才由資料來源彙整發布,或標記為統計區間之起點而值為整個區間之彙總,區間延伸到其後之棒),須自行把它標在得知時點所落之棒(下一棒或更後),否則挑選函數會用到當時尚不知之資訊 —— 評估器只能依標記之時間對位,**無從檢查**時間標記是否誠實。建帳本時於帳本終點(`endTime`)截斷:標記時間 ≥ 終點之列不入帳本,故帳本內之序列不含「標記時間在終點以後」之列所帶之值(訓練期帳本之序列即不含其後之期間,且為評估帳本之前綴)。截斷以字串比較 K 線之 `time` 與 `endTime`(與 K 線本身之截斷相同):`endTime` 須與 K 線之 `time` 同一字串格式、且落在棒界。**名稱集合須事前固定**:`ctx.meta.seriesNames` 列出全部序列之名稱,不得讓檔案之有無隨未來事件之發生與否而增減(名稱本身即是資訊)。保留期等另建之帳本,若要評估用到外部序列之成品,須以各自之序列夾建入同名之序列,否則該成品於該帳本上拋錯。
- `ctx.meta.ntAll` 是「整段訓練期」之靜態計數(策略庫之屬性,不隨決策日改變);要隨決策日更新之計數用 `ctx.stat(0).entries`。
- 凡是利用「這隻策略在訓練期整體一定賺」之挑法(挑訓練期交易極少者、挑近期最差者賭回升…)在訓練期內分數很高,那是策略庫最佳化造成之性質,不代表在回測期有效;一切以回測期之評估為準。
- 評估器**不提供**策略求解時的樣本內績效(年化、勝率等);績效一律用 `ctx.stat` 之走勢前向統計。
- 因子名形如 `price_ohlc_none_RSI_rsi_1day`:依序為 來源(price / index)_種類(ohlc / vbs)_輸入欄_輸出欄_指標_週期。
- 進場規則之條件(`ctx.meta.keySym` / `keyTh`)是策略之靜態定義,於各策略之求解窗內求得(與 `tp`、`sl` 同屬結構屬性,不隨決策日改變);各因子之尺度不同,門檻之大小要對照該因子自己之序列(`ctx.factor`)才有意義。

## 4. `accept(sig, book)`(選配之執行規則)

- `sig = { sid, bar, day, dow, mode, k, tag, group }`:這個訊號的策略序號、進場棒、日序號、星期、方向、所屬決策序、`pick` 該次回傳之 `tag` 之快照(`pick` 回傳 `{ ids, tag }` 時才有;唯讀;可放每策略之優先序、市況旗標等;只收可結構化複製之資料,見 §1)、所屬之子帳(見下「分帳」;未分帳為 0)。
- `book = { open, openLong, openShort, openGroup, dayCount, winCount, nAccepted, pnlClosed }`:現有持倉單數(已下單未出場)、其中做多 / 做空數、各子帳之持倉單數(長度 4 之陣列)、當日已下單數、本決策視窗已下單數、累計已下單數、已出場單之累計損益。
- **分帳(選配)**:`pick` 可回傳 `{ ids, tag, group }`,`group` 為與 `ids` 等長之整數陣列(0 ~ 3;各席所屬之子帳;不給 = 全在第 0 帳)。此時 `sig.group` = 該訊號之策略所屬之子帳,`book.openGroup` = 長度 4 之陣列(各子帳現有持倉單數;各帳之和 = `book.open`)。用途:兩條名單之訊號量差很多時,共用一個持倉上限會互相排擠 —— 各帳各設上限,例如 `accept = (sig, book) => book.openGroup[sig.group] < 15`(兩帳合計仍須 ≤ 硬限制)。未回傳 `group` 者 `sig.group` 恆為 0、`book.openGroup[0]` 恆等於 `book.open`,行為與以往完全相同;`group` 不入 `selHash`。各虛無與組成 / 幾何對照之替換沿用被替換之席之子帳。**以方向分帳(做多一帳、做空一帳、兩帳用不同規則)會經由兩側活躍度之不對稱使下單偏在一側,等於把回測期之方向寫進模組**(迴圈檢查「下單流量偏一側」會列出):分帳請依規則或資訊源分,兩帳內各自維持與全庫相近之多空比例。
- 訊號之先後:依進場棒由早到晚;**同一根進場棒之多個訊號,依各策略之 `ctx.meta.tie` 由小到大**(不是依序號)。持倉上限擋單時,先被問到者先得席位。
- 必須是 `(sig, book)` 的純函數:不得讀寫模組層變數(評估器會在操作績效、各新鮮度視窗、虛無各自獨立模擬,各有自己的 `book`)。兩個物件會被重複使用,不要保存引用;它們是封裝之交出物件,每次呼叫前由評估器以自己之計數重寫 —— 改它們不改評估器之持倉計數與任何數字(把欄位設為不可寫等改動使評估器寫不進者,該次評估失敗)。
- 硬限制:**月均單 ≤ 400、最大同時持倉 ≤ 50**,超過即否決;沒有 `accept` 時選集稍大就會超過持倉上限,所以多半需要它(例如 `book.open < 30`)。

## 5. 評估指令

```bash
node g_eval.mjs --pick <你的模組.mjs> --mode quick                       # 迭代用: 回測期;相位 0 與 3、7 日地平線、不算虛無(約 10 秒)
node g_eval.mjs --pick <你的模組.mjs> --mode full --out <結果.json>      # 交付用: 回測期;七相位、1/3/7/14/30 日新鮮度、同劑量虛無 64 抽(約 30 ~ 60 秒)
node g_eval.mjs --pick <你的模組.mjs> --mode quick --period train        # 診斷用: 改看訓練期內之決策(樣本內;不計入判讀)
node g_eval.mjs --pick <你的模組.mjs> --mode full --period postfit       # 診斷用: 求解窗後段(只留求解窗已結束之席;非正本;不印判讀;見上方之效度限制)
```

輸出怎麼讀(未註明者皆為**回測期**之數字):

- **操作績效**:等效年化之七相位平均、最差相位、最佳相位;月均單;最大同時持倉;勝率;下單率(有 `accept` 時)。
- **新鮮度**:選集於其後 1 / 3 / 7 / 14 / 30 日內之等效年化(七相位平均)。短地平線之數字天生偏大(持倉需求小),只與同地平線互比。
- **同劑量虛無**:同樣的決策日、每次選一樣多隻、同樣的 `accept`,但改成隨機選;重複 64 次。`p` = 隨機不輸你的比例,**p ≤ 0.05 才算你的挑法有內容**;「超額」= 你的七相位平均 − 隨機挑之平均。回測期內隨機挑之等效年化為負 —— 贏過隨機挑只是第一步,**目標是本身為正且各相位皆為正**。
- **判讀**:`S` = 0.7 × 七相位平均 + 0.3 × 最差相位。階梯:1 = `S ≥ 15` 且各虛無(同劑量;有算時另含同訊號量、同活躍度、同側同活躍度)之 `p ≤ 0.05`;2 = 各地平線之新鮮度皆 ≥ 10 且最差相位 ≥ 5;3 = 月均單 ≤ 300 且最大同時持倉 ≤ 30。
- 持倉上限越小,等效年化之絕對值越大(分母是最大同時持倉),同劑量虛無也跟著變;不同持倉上限或選集大小之 `S` 不能直接比,要看「超額」與 `p`。
- **同訊號量虛無**(選集之每隻訊號數偏離全體隨機逾 10% 時才有):同劑量虛無只匹配「隻數」,但等效年化受訊號量之影響很大;此列改與「訊號量相當之隨機選集」比較。階梯 1 亦要求其 p ≤ 0.05。
- **同活躍度虛無**(與同訊號量虛無同時出現):每次決策把全部策略依「決策日以前之累計進場數」分為 10 層(同值者同層),隨機選集自各層抽與成品相同之隻數 ⇒ 隨機選集之活躍度分層與成品相同。選集較活躍或較安靜時,**臂之內容以本列之超額與 p 為準**(階梯 1 亦要求其 p ≤ 0.05):只是挑得較安靜或較活躍者,其差值會留在同訊號量之比較內,由本列扣除。成品若把某幾層之策略全數取走,隨機選集即成品本身,本列之超額為 0。
- **同側同活躍度虛無**(組成對照;完整評估一律算出;結果檔之 `metrics.nullSideAct`):把選集之**每一隻**換成「同方向、決策日以前累計進場數之名次 ±50 名內」之隨機一隻(各側分別排名)⇒ 隨機選集與成品同方向比例、活躍度逐隻相近。回測期內多空行情不對稱,且越活躍之策略其方向曝險越大:**「方向 × 活躍度」之組成本身就有績效**,同活躍度虛無(不分方向、只分 10 層)扣不掉它;全體之每隻訊號數與隨機相近,也不代表逐隻之活躍度相近。**有沒有挑選內容以本列之超額與 p 為準**;`triggered` = 選集之每隻訊號數或做多比例偏離全體隨機逾 10%(此時階梯 1 亦要求其 p ≤ 0.05);`share`(組成可重現之比例)= 本虛無之均 ÷ 成品之等效年化,接近 100% 表示換成同組成之任意策略也一樣好(0 = 組成是逆風);`thirdsMean` = 各三等分段內本虛無之均(與成品之三等分並列,看超額是否只集中於某一段)。側別或活躍度本身即由當下狀態決定之機制,其內容在組成之選擇,須另以**同比例、隨機時機之安慰劑**(保留成品之狀態比例、只打亂時機,至少 2 抽;共用工具區有樣板)證明,並以 `--period train` 之 tag 比例證明它會切換;把判定依據換成落後窗之安慰劑會同時改變狀態比例,只在其比例與成品相差 < 10% 時才可用來判時機。
- **同側同幾何同活躍度虛無**(幾何對照;`metrics.nullSideGeo`;只供判讀、不入階梯):在上列之外再匹配「該側內止盈三等分 × 止損三等分」(同值依 `tie`;兩個等分各自劃分)。選集之止盈 / 止損比全體寬或窄時,由此看優勢是否只是挑到某種幾何;欄位同上(另有 `nTp`、`nSl`)。
- **損益歸因**(各相位平均;只增輸出):`metrics.op.pnl` = 已下單之損益和(每單 1 單位);`metrics.op.bySide` = `{ long: { orders, pnl, winRate }, short: { … } }`(依策略之方向);`pick` 有回傳 `tag` 時另有 `metrics.sel.tagPerf` = `[{ tag, decisions, orders, pnl, pnlPerOrder }]`(每張單歸到其所屬決策之 tag;逾 64 種者其餘併為末筆)。`metrics.op.byGroup` = `[{ group, seats, orders, pnl, winRate }]`(每張單歸到其策略所屬之子帳,見 §4「分帳」;`seats` = 該子帳每次決策之平均席數;只列有席或有單之子帳,未回傳 `group` 者只有子帳 0 一列 = 全體)—— `group` 只當標籤(`accept` 不讀子帳)之合成,亦可由此直接讀各線於合成內實際分到之下單數與損益。兩側之 `pnl` 和 = 各子帳之 `pnl` 和 = 各 tag 之 `pnl` 和 = `op.pnl`。要回答「損益來自哪一側」「哪一條線在賺」「哪一種狀態在賺」時直接讀它,不必另跑單側或單線之評估。
- **同一進場棒之訊號次序是 S 之雜訊來源**:下單率低(多數訊號被持倉上限擋下)之成品,同一根進場棒之多個訊號誰先被問到(§4;依 `ctx.meta.tie`)會決定誰得席位,S 隨之變動 —— 實例:下單率約 22% 之合成,只換此次序 S 即在 84 ~ 95 之間。這種成品之兩個版本,**S 之差小於此帶寬者不據以判定**;帶寬以擴充診斷之 `api.simulate` 之 `opts.orderSalt` 量(§7),下單率 100% 者不受影響。
- **評估期間三等分**(`metrics.op.thirds`):把評估期間之決策依序分成三段,各段自空倉起算、各自計等效年化(七相位平均與最差相位);完整評估另給各段隨機挑之均(`nullMean`)。績效集中在某一段者,不是穩定之正績效。
- **下單集中度**(各相位平均):實際下單之不同策略數與其不同因子組合數、下單最多之前 1% 進場棒占全部下單之比例、單一進場棒之最多下單數。選集很大而下單率低時,由此看實際下單者是否集中在少數策略或少數進場棒(結果由少數事件主導)。
- **選集組成**:每隻被選策略於每個決策視窗(7 日)之訊號數、做多比例(括號內為同劑量虛無 = 全體隨機之值)、平均因子數、平均止盈 / 止損。分數受選集之交易活躍度與多空比例影響很大(回測期內多空行情並不對稱);比較兩個版本時先看這一列是否不同。
- **與參考模組之選集重疊率**(加 `--ref <參考模組.mjs>` 才有):另以參考模組之 `pick` 於同相位、同亂數種子逐決策執行(各有自己的 `ctx.state` / `ctx.rand`,與本模組互不影響),輸出每次決策「交集 ÷ 本模組之選集大小」之平均與 p10 / 中位 / p90,依決策段分列(各相位最前 10%、中段、最後 10% 之決策);另給「交集 ÷ 參考選集」之平均。只增輸出(結果檔之 `refOverlap`),既有數字與 `selHash` 不變。**可一次給多個參考**(逗號分隔:`--ref a.mjs,b.mjs`):`refOverlap` 為第一個參考,另有 `refOverlaps` = 全部參考依序之陣列 —— 要對兩個以上之參考量重疊率時,評估一次即可,不要為每個參考各跑一次。要回答「這個變體把名單換掉多少」「與某成品是否為同一份名單」時用它,不必自己在 `tag` 內算;參考模組若在別的工作夾,先複製進自己的工作夾。交付用之 `result_full.json` 不帶 `--ref`。
- **成員重抽之重放**(加 `--member <鹽>:<0|1>` 才有):只把策略庫之一半交給同一個模組(`0` = 甲半、`1` = 乙半;鹽為 0 ~ 4294967295 之整數,十進位或 `0x` 開頭之十六進位;換鹽 = 換一種切法;切法 = 各策略「於全庫之序號經雜湊」所得之同分次鍵之基底(即未帶 `--tie-salt` 時之 `ctx.meta.tie`)`tie` 與鹽之雜湊 `((Math.imul(tie ^ 鹽, 2654435761) >>> 0) / 4294967296) < 0.5` 者為甲半;`--tie-salt` 只改交出之 `ctx.meta.tie`,不改切法)。**模組不必改寫**:`ctx.n` 為半庫之隻數,`ctx.meta` 之各陣列與 `ctx.stat` / `orders` / `entryDays` / `entryBars` / `exitDays` / `exitBars` 皆為半庫內之序號,各策略之 `ctx.meta.tie` 與其於全庫時相同;期間、相位、虛無(自半庫內抽)、擴充診斷照舊;模組內跨策略之彙總(家族和、分位門檻、資格池)因而亦只計半庫內之策略。用途:檢驗成品之內容是否依賴特定成員(「換一批策略」之重複)。**此結果不是正本**:畫面首列註明,結果檔另帶 `member{ tag, salt, half, n, nFull }`(失敗之結果檔帶 `member{ tag, salt, half }`)、評估紀錄之該列(含失敗者)帶 `member`;`selHash` 依序號而定,一般與全庫者不同(以 `member` 標記辨識,不以 `selHash` 之異同判斷);交付用之 `result_full.json` 不帶此旗標。每次評估照常記入評估紀錄(`--ext-test` 試跑成功時不記評估紀錄,不在內;`--mode full` 之成功評估另計入完整評估次數)。格式不合或旗標重複給者不評估(不靜默改用全庫),印 `invalid --member: must be <salt>:<half> …`、離開碼 2。半庫帳本之 `dir` / `meta` 沿用全庫之資訊,策略檔名須以 `srcIdx` 對應(`loadIds(dir)[srcIdx[i]]`)。
- **selHash**:選集與下單序列之指紋;同一模組重跑必須相同。
- **選集大小之分佈**:各決策之選集大小之 p10 / 中位 / p90、空選集之決策比例;`pick` 有回傳 `tag` 時另列各 tag 之決策比例(關掉某側、依狀態切換席次之機制,可直接由此看作用頻率)。結果檔之 `metrics.sel.tags` **列出全部 tag**(逾 64 種者其餘併為末筆),`metrics.sel.tagKinds` 為種數;**全部 tag 皆為數值時另給 `metrics.sel.tagStats`**(`{ n, mean, p10, p50, p90 }`,以決策為單位)—— 以數值 tag 作診斷量(例:選集之平均鍵值)時直接讀它,不必由所列之比例手算加權平均。畫面只印前 8 種。
- 位於節點 / 做夢工作夾內之模組,每次評估會在該資料夾之 `.evals.log` 留一列紀錄(迴圈據以計數評估次數);不要刪改它。`--no-log`、`--seed`(換亂數種子)與 `--tie-salt`(換同分次序)只供迴圈重跑使用:節點帶 `--no-log` 者照樣記錄並列為迴圈檢查之問題,帶 `--seed` / `--tie-salt` 者不生效。迴圈重跑時會**同時換亂數種子與同分次序**(`ctx.meta.tie` 與同一進場棒之訊號先後)另重放數次,其 S 列於節點文件;主鍵大量同分(名次、計數、勝率、「無交易 = 0」)之成品,入選者實際由 `ctx.meta.tie` 決定,換次序後由正轉負者會被列為「分數不穩」—— 交付前可用共用工具區之 `snippets/tieAlt.mjs` 自檢。紀錄含模組內容之雜湊:**已完整評估之版本,交付時工作夾內須仍有內容相同之檔**(評估後又改寫該檔者,列為「無檔可重現之版本」)。
- 全機之 CPU 或記憶體逼近上限時(同輪之其他節點也在評估、或機器另有負載),評估會先等一下再開始(至多約 90 秒,輸出會註明等了幾秒);不影響結果,不必重跑或中斷。

## 6. 常見錯誤

- 跨決策保存 `ctx.stat()` 回傳之陣列(下次呼叫已被覆寫)。
- 對全部策略逐一呼叫 `ctx.orders(s)`(極慢);先用 `ctx.stat` 篩到幾百隻再細看。
- 排序未處理除以 0 / NaN,或未給決定性之次序。**同分時以 `ctx.meta.tie[s]` 為次鍵,不要用序號**:序號是策略檔之排序位置,帶有資訊;勝率、計數等粗鍵大量同分時,序號會變成隱藏之排序鍵。寫法:`cands.sort((a, b) => key(a) - key(b) || ctx.meta.tie[a] - ctx.meta.tie[b])`。
- 把持倉上限、每日上限、選集大小當成調 S 之旋鈕:等效年化之分母是最大同時持倉,取消日上限、壓低持倉上限、放大選集都會機械性地抬高 S(同劑量虛無也跟著升),那不是挑選之內容。節點任務之中性預設為 `book.open < 30`、不設日上限、選集 40。
- 回傳空陣列過多(全程無單 ⇒ 否決)。
- `accept` 使用模組層變數計數(各模擬互相污染,且重跑不一致)。
